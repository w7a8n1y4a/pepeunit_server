# Правила работы агентов в Pepeunit Backend

Эти правила применяются ко всему репозиторию, включая Python Backend, Go DataPipe, тесты и миграции. Перед изменениями прочитать этот файл и [карту существующих паттернов](instruction/150_to_160/backend-patterns.md).

## Git: коммиты запрещены

- Агенту **запрещено коммитить изменения**. Не выполнять `git commit`, `git commit --amend` и другие операции, создающие или переписывающие коммиты, в том числе через API, IDE, скрипты и подагентов.
- Не выполнять `git add`, `git push`, не создавать теги. Не изменять существующий индекс и чужие изменения. Коммиты и публикацию выполняет владелец.
- Результат работы — изменения в рабочем дереве, просмотренный diff и отчёт о проверках. Поле commit/MR: «не создан, коммиты агентам запрещены». Чтение HEAD, истории, status и diff разрешено.
- Передавать этот запрет в каждое задание исполнителю и ревьюеру, в том числе при работе в соседних репозиториях.

## Принцип: проверять границы, доверять установленным контрактам

Внешний ввод проверяется при входе. После успешной проверки внутренние функции используют конкретные типы и обязательные поля напрямую. Не добавлять защитные ветки на случай, если корректный вызывающий код вдруг нарушит свой контракт.

Аннотация типа сама по себе не проверяет входные данные. Прежде чем полагаться на контракт, проследить реальные вызовы, конструктор/фабрику, валидацию и контракт возврата. Если гарантия отсутствует, установить её в месте, отвечающем за данные; не размножать проверки по всем потребителям.

## Слои и зависимости

- `app/routers/v1/` — HTTP-параметры, зависимости, вызов сервиса и схема ответа. Не добавлять здесь SQL, бизнес-правила и локальные копии обработчиков доменных ошибок.
- `app/schemas/pydantic/` — схемы входа/выхода и фильтры; `app/validators/` — профильная валидация. Новые проверки формы данных помещать в существующий подходящий валидатор/схему.
- `app/services/` — бизнес-сценарии, авторизация, последовательность операций и доменные проверки. Повторно использовать сервисы из HTTP, бота и фоновых сценариев, а не копировать правила в транспорт.
- `app/repositories/` — доступ к хранилищам и внешним системам, запросы и преобразование их результатов. Использовать `BaseRepository`, существующие репозитории и helpers, когда их контракт подходит.
- `app/domain/` — SQLModel-сущности, поля и ограничения БД; `app/dto/` — внутренние структуры и перечисления.
- `app/configs/rest.py::ServiceFactory` собирает зависимости. При ручном вызове передавать реальные зависимости явно: `Depends(...)` разрешает FastAPI, а не Python-конструктор сам по себе.
- Сохранить текущие границы транзакций: `BaseRepository.create/update/delete` уже делают DB commit. Не добавлять второй commit в сервис «для надёжности». Многошаговую атомарную операцию проектировать явно; несколько вызовов этих методов не являются одной транзакцией. DB commit не относится к запрету Git-коммитов.
- Авторизация находится в `AccessService` / `AuthorizationService`. Проверка формы запроса не заменяет проверку прав. Не переносить права исключительно в HTTP-router: сервисы вызываются и другими транспортами.

## Типы, атрибуты и отсутствие значений

**Запрещено в новом внутреннем бизнес-коде:**

- `getattr(obj, "known_field", default)`, `hasattr`, `obj.__dict__.get(...)`, `try/except AttributeError` для доступа к известным полям модели или сервиса. Использовать `obj.known_field`.
- `isinstance` / `type(...)` для перепроверки конкретного типа, уже установленного схемой, конструктором или вызывающей функцией.
- Ветки `if dependency is None`, `if model is not None` после успешного получения обязательной зависимости/объекта, а также повторные `is_valid_object` на том же неизменённом результате.
- Расширять аргументы до `Any`, `object`, `dict | Model | None` только ради универсальности; принимать и «сырой», и проверенный формат на каждом уровне.
- Прятать нарушение обязательного контракта за `None`, `[]`, `{}`, `False`, нулём, `getattr` с default, `dict.get` с default или `value or fallback`.
- Заменять лишний `if` на такой же лишний `assert`, `cast`, `# type: ignore` или обёртку `safe_*` / `ensure_*`.

**Допустимые случаи с реальной семантикой:**

- `repository.get(...)` действительно может не найти строку. В месте, которому требуется объект, один раз использовать `is_valid_object(obj, NotFoundEntity.…)`, затем обращаться к полям напрямую. Не писать `obj = is_valid_object(...)`: helper возвращает `None` при успехе.
- Nullable-поле БД, необязательный параметр, состояние «ещё не загружено», промах кэша или отключённая возможность действительно допускают отсутствие значения. Обрабатывать его там, где определяется соответствующее поведение.
- Для PATCH/фильтра `None`, отсутствие поля, `False`, `0` и пустое значение могут означать разное. Сохранить контракт конкретного API. Не заменять `is not None` проверкой истинности; не применять `remove_none_value_dict` к контракту, в котором `null` означает очистку.
- `isinstance` допустим для сырого внешнего значения в валидаторе, объявленного union или реального полиморфизма, когда варианты требуют разного поведения. После нормализации не повторять эту проверку ниже по стеку.
- Динамический доступ допустим только для действительно динамического имени (например, общего обхода метаданных) или изолированного адаптера внешней библиотеки с различающимся контрактом. Фиксированное имя известного поля — не такой случай. Не превращать это исключение в универсальный fallback.

Для каждого нового защитного условия уметь указать конкретный источник варианта, а не «на всякий случай». Неочевидную границу объяснить коротким комментарием или в описании изменения. Валидация нового сетевого запроса, новая загрузка из БД и изменение состояния между вызовами создают новую границу; прежняя проверка не гарантирует неизменность внешнего мира.

## Ошибки и обработчики

- В Python использовать доменные исключения из `app/configs/errors.py` и обязательный `code=ErrorCode.…` из `app/configs/error_codes.py`; в Go — существующий `internal/apperr`. Сохранять стабильность существующих числовых кодов и формат API.
- `CustomExceptionMiddleware` уже преобразует доменные ошибки в HTTP-ответ. Не добавлять `try/except CustomException` в каждый router/service для той же работы.
- Перехватывать конкретную ожидаемую ошибку там, где можно восстановиться, перевести её в доменную ошибку, откатить транзакцию или завершить задачу с корректным статусом. При переводе сохранять причину через `raise … from err`.
- Запрещены `except: pass`, `except Exception: return None/[]/{}/False`, необоснованное `contextlib.suppress`, обработчик, который только повторно выбрасывает ту же ошибку, и логирование одного сбоя на каждом уровне.
- Общий `except Exception` допустим на владельце жизненного цикла фоновой задачи/сообщения, если он фиксирует неуспех, освобождает ресурсы и определяет дальнейшее поведение. Пример роли — `OperationTaskService._execute_background`; это не разрешение глотать ошибки в произвольных методах.
- Не преобразовывать внутренние `AttributeError` / `TypeError` в ошибку пользовательского ввода. Ошибка реализации должна оставаться видимой. Не перехватывать `BaseException` и не подавлять отмену задач.
- Не вводить обработчики без потребителя, пустые hooks, pass-through классы, middleware и повторные retries без конкретной обязанности. У каждого обработчика должны быть событие, владелец и наблюдаемый результат; HTTP-адаптер сервиса имеет такую обязанность.

## DRY и размер изменений

- Перед новой функцией искать существующее правило в сервисах, валидаторах, репозиториях и DTO. Переиспользовать совместимый контракт, не копировать его с новым именем.
- Одно правило валидации, сериализации, доступа или расчёта должно иметь одно место реализации для потребителей внутри языка. Общие Python/Go контракты проверять одинаковыми примерами, а не обещанием общего исходного кода.
- Общую повторяющуюся логику извлекать на уровень, которому она принадлежит. Не строить универсальный engine, набор стратегий или новый базовый класс ради одной операции либо похожих строк с разным смыслом.
- Не плодить `utils` и обёртки над одиночным вызовом без самостоятельного контракта. Предпочитать конкретный метод/тип и прямой код.
- Не добавлять совместимость с несуществующими вариантами стека и старыми форматами без требования задачи. Совместимость, нужная миграции, должна иметь явные версии, границу и проверки.
- Не исправлять весь старый код попутно. Старые fallback, дублирование и неточные аннотации не дают разрешения повторять их. Существенное изменение общего контракта выделять отдельно, учитывая вызывающие места.

## Настройки, ресурсы и Go

- Использовать `settings` для конфигурации запуска и `runtime.get()` для настроек инстанса. `runtime.get()` возвращает `InstanceSettings` либо выбрасывает ошибку; не проверять его результат на `None`, не читать `.env` повторно в сервисах и не подставлять фиктивные значения при сбое БД.
- Фоновая задача владеет своей сессией/клиентом и закрывает ресурс. Не передавать request-scoped SQLAlchemy Session в поток или отложенную задачу после завершения запроса. Сохранять правила конкурентного доступа и отмены.
- Go DataPipe расположен в `data_pipe/`; использовать существующие пакеты `internal/types`, `database`, `datapipe`, `apperr`. Не создавать альтернативный процесс или контейнер без задачи на изменение архитектуры.
- В Go проверка `err != nil` необходима по контракту возврата и не является запрещённым defensive-кодом. Не удалять её ради сокращения проверок. Не дублировать `nil`-проверки обязательных зависимостей после успешной инициализации; реальные optional-поля и отсутствующие записи обрабатывать.
- Не обходить типизацию через `reflect`, `any` и цепочки type assertions для известных структур. Декодировать внешние данные на входе; использовать типизированные структуры внутри.

## Проверки и сдача результата

- Следовать установленным версиям и Ruff-конфигурации в `pyproject.toml`; не менять toolchain и зависимости ради удобства задания.
- `make lint` выполняет `ruff check --fix` и меняет файлы. Для проверки использовать `uv run ruff check <изменённые Python-файлы>`; перед запуском убедиться, что окружение подготовлено. Не применять массовый autofix к чужому коду.
- Модульные тесты находятся в `app/**/test_*.py` (`make test-module`); интеграционные — в `tests/` (`make test-integration`). Импорт `app` загружает настройки через `.env`; не считать любой модульный запуск изолированным автоматически. Интеграционные и нагрузочные проверки выполнять только на подтверждённом тестовом окружении.
- Проверять изменённое поведение и значимые границы, не закреплять тестами лишние внутренние проверки. Использовать реальные DTO и mock со `spec`/`autospec` там, где это подходит; не менять продуктовый контракт ради неполного mock.
- Перед сдачей проверить каждый добавленный `getattr`, `hasattr`, `isinstance`, `None` guard, fallback и `except`: есть ли реальный источник варианта, уже установленная гарантия, существующий helper и конкретное действие при ошибке? Это ревью смысла, не механический запрет слов.
- В отчёте указать изменения, проверки/пропуски и ограничения. Коммиты запрещены, результат оставлять в рабочем дереве.
